How SVI Values xSOL

Where the number comes from, who touches it on the way, and why no one has to be trusted with the arithmetic. Every figure on this page is from the first on-chain publication earlier today.

The Pyth question

SVI depends on Pyth. Pyth does not depend on SVI — not yet. Pyth answers one question, “what is 1 SOL worth in dollars right now”, and gets it from exchanges. The value of xSOL is calculated from that answer plus Hylo's own books. So Pyth is upstream of us, and we are upstream of lenders. What could flip in future is the other direction: once SVI publishes xSOL's value on-chain, an oracle network could consume it to offer an “xSOL/USD” feed — that would be Pyth depending on us, for xSOL.

What xSOL is, in one example

Hylo takes in SOL (as liquid-staked SOL) and issues two tokens against it. hyUSD is a stablecoin: always worth $1. xSOL is what's left over — it owns everything in the vault that isn't owed to hyUSD holders. That makes xSOL a leveraged claim on SOL: when SOL moves 1%, xSOL moves about 2.5%.

So xSOL's fair value is not a market opinion. It's a subtraction:

Collateral ratio $25.4M ÷ $15.4M = 1.65×; leverage $25.4M ÷ $10.0M = 2.5×. Those two ratios are what Hylo's rebalance zones and SVI's status flags are about. The exact figures use Hylo's integer math; the rounded ones here are for reading.

Notice what the formula needs: the SOL price (from Pyth), and Hylo's books (from Hylo's on-chain accounts). Nothing else. And notice what nobody publishes: the result. Hylo's website computes it in your browser; no on-chain account holds it. A lending protocol that wants to accept xSOL as collateral has had two bad options — trust an off-chain server, or use the DEX price, which a trader with a few million dollars can move. SVI's job is to compute that result on-chain and put it in a public account.

Who depends on whom

One consequence worth saying plainly before any video: our quote can never be fresher than the SOL price it was computed from. Hylo's own rule is that a SOL price older than 10 seconds is unusable, and SVI inherits that rule unchanged — the adapter refuses to publish rather than publish from a stale input.

The whole system

Four kinds of things, in four colours. Grey already exists on Solana and SVI changes none of it. Violet is what SVI deploys. Amber is the product: one account. Blue is anyone who reads it.

What happens on one refresh

This is the sequence that ran at 23:41 today. It takes one transaction and about 13,000 compute units.

  1. keeper · anyone

    Send the transaction

    The keeper builds one instruction, refresh_xsol_nav, listing nine accounts: Hylo's state, the xSOL mint, Pyth SOL/USD, the feed descriptor, the quote account, the adapter's config and signing address, and svi-core. It pays the fee. That is its entire power.

    Example: the test used the default wallet in ~/.config/solana/id.json. It could have been any wallet; the result would be byte-identical.

  2. svi-hylo-adapter

    Check that every account is the real one

    The keeper chose which accounts to pass in, so the adapter trusts none of them by position. Hylo's state must be owned by Hylo's program and sit at Hylo's known address. The mint must be xSOL. The Pyth account must be the one Hylo's own state names as its oracle — so the adapter cannot disagree with Hylo about which price is authoritative, by construction.

    If a keeper passed a fake Pyth account with a flattering price, step 2 fails with OracleMismatch and nothing is written.

  3. svi-hylo-adapter → hylo-core

    Ask Hylo's own code whether the state is usable

    The adapter hands the accounts to hylo-core, the same Rust library Hylo's program uses, pinned to one exact commit. It runs five checks: the collateral cache is from the current epoch, the Pyth update is fully verified, its publish time is within Hylo's 10-second window, its slot is within 25 slots, and its confidence interval is within Hylo's tolerance. SVI reimplements none of this.

    Example from tonight: publish time 1789065304, clock 1789065305 — one second old. Any check failing is a refusal with a specific code: HyloCacheStale, OracleStale, OracleConfidenceTooWide.

  4. svi-hylo-adapter → hylo-core

    Compute the value, twice

    Hylo quotes xSOL two ways: what you'd get redeeming one (floor, against the lower SOL price bound) and what you'd pay minting one (ceiling, against the upper bound). SVI publishes the redeem value as the headline — what a liquidator could actually realise — and both as the bounds.

    redeem NAV → value, lower$0.060285498 mint NAV → upper$0.060315053 band4.9 bps of value
  5. svi-hylo-adapter

    Decide: publish or refuse

    The band must be no wider than the feed's tolerance (500 bps). Bounds must be coherent. Then the adapter sets flags that describe the state honestly rather than hiding it: tonight's was BUY_ZONE, meaning Hylo's collateral ratio put it in a rebalance buy zone. If Hylo were underwater, the adapter would publish exactly zero with DESTABILIZED set — a loud, correct answer, not a quiet wrong one.

    Every refusal leaves the previous quote in place to age past its valid_until_slot. Fail stale, never fail wrong.

  6. svi-hylo-adapter → svi-core

    Publish over a frozen byte format

    The adapter calls svi-core with a 96-byte message: an 8-byte instruction id and 88 bytes of value, bounds, slot, timestamp, a hash binding the quote to the exact input accounts, and flags. It signs with a program-derived address only this program can sign for. The two programs share no Rust code — they're built on incompatible framework versions — which is why the format is bytes, checked by tests on both sides.

  7. svi-core

    Check the writer, then write

    svi-core does no arithmetic. It checks that the signer is the adapter address recorded in the feed descriptor when the feed was created, that the feed is active, then writes the 320-byte quote: sequence becomes 1, valid_until becomes the observed slot plus 750 (about five minutes).

    Result: signature 4h8kfqwA…8ui3f, and an independent off-chain recomputation over the same accounts returned $0.060285498 — identical.

What a reader does with it

The account is 320 bytes with fixed offsets, so a program reads it with no library and almost no compute. This is the entire integration for a lender:

Example · a lending market accepting xSOL

A user deposits 100,000 xSOL. The market reads the quote account in the same transaction:

valid_until 445954195 ≥ current slot?yes → usable flagsBUY_ZONE only → no DESTABILIZED, no HALTED collateral value (lower bound)100,000 × $0.060285498 = $6,028.55 at 60% LTV, may borrow$3,617.13

Five minutes later, if no keeper has refreshed, valid_until is in the past. The market should refuse new borrows against xSOL and leave existing positions alone until a fresh quote lands. It never has to guess whether a stale number is “probably fine”.

What exists today

Built and proven

  • svi-core and svi-hylo-adapter, compiled for Solana, 17 tests
  • svi-abi: the 96-byte format, zero dependencies, checked from both sides
  • First on-chain publication over real mainnet state, matched off-chain to the last digit
  • svi-keeper: permissionless crank, and a watcher for the quote
  • Morning validation: SVI's off-chain reading matched hylo.so's displayed $0.0614 exactly

Not yet

  • Mainnet deployment (tonight's run was a fork of mainnet state)
  • methodology_hash is zero until the spec document is frozen
  • The independent observer and the mirror API
  • Epoch-boundary handling via Hylo's own cache update
  • A second adapter, which is where the “interface” in the name gets tested

Words used above

NAVNet asset value: what one token is worth by the protocol's own books, as opposed to what someone will pay for it on a DEX.
PDAProgram-derived address. An address with no private key; only the program it belongs to can sign for it. It's how a program proves “this came from my code”.
CPICross-program invocation: one program calling another inside the same transaction.
SlotSolana's clock tick, about 400 ms. 750 slots ≈ 5 minutes.
bpsBasis points; 100 bps = 1%. Tonight's band was 4.9 bps, or 0.049%.
KeeperAny wallet that sends the refresh transaction. It has no authority; it only pays.
SurfnetA local copy of mainnet's state, used for tonight's run. Same bytes, local validator.
