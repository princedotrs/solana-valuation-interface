What that run actually proves

  1. svi-hylo-adapter

    It read Hylo's real state

    The state PDA, the xSOL mint and the Pyth SOL/USD account Hylo itself names as its oracle — each verified by owner and address before a field was touched.

  2. hylo-core

    It used Hylo's own math

    The same library Hylo's program uses, pinned to one commit and recorded on-chain. SVI reimplements none of it.

  3. CPI · svi-core

    It wrote through one door

    A 96-byte message signed by the adapter's program-derived address. No human holds a key that can write this account.

  4. verification

    An outsider got the same number

    An independent off-chain recomputation over the same accounts and the same clock returned $0.060285498 — identical to the last digit.

The problem

Nobody publishes this number

xSOL is Hylo's leveraged SOL token. Its value is not a market opinion — it is a formula over Hylo's own books. No oracle carries the result; Hylo's website computes it in your browser.

So when an oracle network wanted an xSOL feed, it asked Hylo to read its own protocol over RPC, do the math on a server, and hand a number to an API. Hylo's founder said this in public:

“honestly an accepted smart contract interface for pricing onchain assets would be amazing — bc pyth wants us to read our own protocol by RPC and give them data by an API — it leaves all sorts of unimaginable security holes”

— Plish, Hylo founder · public post, 28 August 2026

He is right. That pipeline has five trusted hops and a consumer can check none of them. This failure class already has a body count.

$5.8M · Loopscale

Apr 2025, Solana. The lender's own pricing of RateX PT tokens was wrong. Undercollateralised loans drained 12% of TVL two weeks after launch.

$1.8M · Moonwell

A config change priced cbETH via cbETH/ETH only, dropping the ETH/USD leg. It read $1.12 instead of ~$2,200.

wUSDM · Venus

Feb 2026. A donation attack moved the ERC-4626 share exchange rate itself, then self-liquidated against it. The rate was the attack surface.

$10.2M · YieldBlox

Feb 2026. A thin-liquidity VWAP oracle on a tokenised-treasury pair inflated collateral value enough to over-borrow.

In every case no on-chain account was ever wrong. The loss came entirely from the valuation layer between true state and the consumer.

Architecture

Four kinds of thing, one write path

Grey already exists on Solana and SVI changes none of it. Violet is what SVI deploys. Amber is the product: one account. Blue is anyone who reads it.

One refresh, start to finish

One transaction, about 13,000 compute units, every read from the same slot.

  1. keeper · anyone

    Send the transaction

    Nine accounts and an instruction id. The keeper pays the fee. That is its entire power — a different wallet would produce a byte-identical result.

  2. adapter

    Check every account is the real one

    Hylo's state must be owned by Hylo's program at Hylo's known address. The mint must be xSOL. The Pyth account must be the one Hylo's own state names — so the adapter cannot disagree with Hylo about which price is authoritative, by construction rather than by diligence.

  3. hylo-core

    Ask Hylo's code whether the state is usable

    Five gates: the collateral cache is from the current epoch, the Pyth update is fully verified, its publish time is inside Hylo's 10-second window, its slot is within 25, and its confidence is inside Hylo's tolerance. Each failure has its own error code and its own remedy.

  4. hylo-core

    Compute the value twice

    Redeeming one xSOL (floor, against the lower price bound) is the headline — what a liquidator could actually realise. Minting one (ceiling, upper bound) is the upper bound. Both are published.

  5. adapter → svi-core

    Publish, or refuse

    The band must be within tolerance and the bounds coherent. Flags describe the state honestly — if Hylo were underwater the adapter publishes exactly zero with DESTABILIZED set, a loud correct answer rather than a quiet wrong one. Then svi-core checks the signer and writes.

Try it · 3 of 3 · integration

Three ways to consume it

One of them covers almost everyone: read 320 bytes at fixed offsets. No SDK required, no API key, no server between you and the number.

99% of usage. One account read, about 200 compute units, inside your own instruction. The layout is frozen and asserted by a test.

// inside your own Solana program
let q = &ctx.accounts.svi_quote.data.borrow()[8..];

let valid_until = u64::from_le_bytes(q[280..288].try_into()?);
let flags       = u64::from_le_bytes(q[296..304].try_into()?);
let base_amount = u64::from_le_bytes(q[224..232].try_into()?);
let lower       = u64::from_le_bytes(q[240..248].try_into()?);

require!(Clock::get()?.slot <= valid_until, MyError::StaleQuote);
require!(flags & HALT_MASK == 0,            MyError::FeedHalted);

// The quote reads "base_amount base units are worth `lower` .. `upper`".
// So value = your amount * lower / base_amount — no decimals hardcoded,
// which is what makes the same four lines work for any feed.
// Here: base_amount = 1_000_000 (one whole xSOL, 6dp), and the
// result is USD at the quote's 9 decimals.
let collateral_usd = amount_xsol as u128 * lower as u128 / base_amount as u128;

High-stakes only. Include the adapter's computation in your own transaction, so the value is derived from this exact slot's state atomically. More accounts, ~13k compute units, zero staleness. Most integrators never need this.

// pass the adapter's nine accounts through your instruction
let cpi = CpiContext::new(adapter_program, RefreshXsolNav {
    payer, config, hylo_state, xsol_mint, sol_usd_pyth,
    descriptor, quote, adapter_authority, svi_core_program,
});
svi_hylo_adapter::cpi::refresh_xsol_nav(cpi)?;

// the quote account is now this-slot fresh; read it as in mode A

For off-chain consumers. A photocopier, not a calculator: it fetches the account through two independent RPCs, requires byte-for-byte agreement, decodes, and serves. It cannot lie about the price, because anyone can compare its output to the account. not built yet

Status

What exists, and what is honestly not done

This is a proof of concept with a working end-to-end path, not a production oracle. The distinction matters and the page will keep saying so until it changes.

ComponentStateWhat it is
programs/svi-coreDONEDescriptor plus the 320-byte quote, layout asserted by test. Accepts a write only from the adapter PDA named in the descriptor.

programs/svi-hylo-adapterDONEVerifies accounts, links hylo-core at a pinned commit, publishes redeem and mint NAV with flags. 17 tests including a live end-to-end run.
First on-chain publicationPROVEN10 Sep 2026 — $0.060285498, band 4.9 bps, exact match with an independent off-chain recomputation.
tools/svi-keeperDONEPermissionless crank with decoded refusal codes, plus a watcher for the quote and for the Pyth input.
hylo-xsol-nav-v1DRAFTThe methodology spec. Complete except five open questions; frozen and hashed before mainnet.
Mainnet · observer · mirror · auditNEXTMainnet deploy ≈ 3.3 SOL, keeper ≈ 0.1 SOL/day. No real collateral should be underwritten against these feeds until a third-party audit.

It ran on a fork, not mainnet

A local validator with Hylo's real mainnet account bytes cloned in. The program bytes and the account bytes are real; the chain is local. Mainnet is the next step.

It depends on Pyth, and always will

Pyth publishes SOL/USD — the input. SVI publishes xSOL NAV — the output, which no oracle carries. Our quote can never be fresher than the price it was computed from; Hylo's own rule rejects anything over 10 seconds old, and SVI inherits that unchanged.

It is one adapter, so far

Until a second protocol ships with no changes to core or the wire format, SVI is a Hylo wrapper. That is the real test of calling it an interface, and it is the next milestone after mainnet.
